MCP protocol & clients

The standardized bridge between AI models and external systems. MCP decouples AI from systems: change servers, not your agent. Below is the message flow between the AI application, the MCP client, the MCP server and the external system.

Layers

Application

AI apps, agents and tools that use MCP. They request context, invoke tools and consume results.

Client

Lives in the host and handles discovery, requests and responses, one per server connection.

Protocol / transport

Standard message format (JSON-RPC 2.0), security, reliability.

Server

Exposes capabilities (tools, resources, prompts) in a standardized way.

Resource

Databases, APIs, files, cloud, SaaS apps, IoT devices: the real systems behind the server.

Protocol highlights

Transport

JSON-RPC 2.0 over stdio for local servers and Streamable HTTP for remote ones (stateless since 2026-07-28, so any instance behind a load balancer can answer). HTTP+SSE is deprecated; WebSocket would be a custom transport.

Message format

Structured JSON requests, responses and notifications. Tool inputs are described with JSON Schema, and outputs can be structured.

Security

OAuth 2.1 authorization for HTTP servers, with Client ID Metadata Documents replacing dynamic client registration. Enterprise gateways add API keys, mTLS and per-tool scopes.

Reliability

Request IDs, error codes, timeouts, cancellation and progress notifications. Make write tools idempotent.

Extensibility

Capabilities travel in every request's _meta and in server/discover. Optional extensions (tasks, MCP Apps, enterprise-managed auth) add features without changing the core.

Design principles

Open spec · human-centric (you stay in control) · secure by default · reliable · composable · future-proof.

What changed in the 2026-07-28 spec

ChangeWhat it means
Stateless coreNo initialize handshake and no session ID. Each request carries its protocol version, client info and capabilities in _meta, so servers scale behind ordinary load balancers. State that must persist is passed as explicit handles in tool arguments.
server/discoverA new method servers must implement, so clients can learn versions and capabilities up front.
Multi round-trip requestsInstead of calling the client back, a server returns input_required with what it needs (for example an elicitation form); the client retries the request with the answers.
Subscriptionssubscriptions/listen replaces the HTTP GET stream and resource subscribe/unsubscribe for change notifications.
CachingList and read results carry ttlMs and cacheScope, and tools come back in a stable order.
Gateway-friendly HTTPMcp-Method and Mcp-Name headers on every Streamable HTTP request.
ExtensionsTasks moved out of the core into an official extension; a formal extensions framework also hosts MCP Apps and enterprise-managed authorization.
DeprecatedRoots, sampling and logging (use tool parameters, direct model APIs and OpenTelemetry instead), the HTTP+SSE transport, and OAuth dynamic client registration. Deprecated features keep working for at least twelve months.

Source: MCP specification changelog, 2026-07-28. See MCP clients for what this means on the wire.

MCP clients

An MCP client is the part of an AI application (the host) that talks to one MCP server. The host runs one client per server connection. Clients don't implement tools: they discover what servers offer, help the model choose, make the requests, handle results and errors, and keep the user in control. This page follows the current specification, 2026-07-28, which made the protocol stateless.

Reading other MCP infographics? Three common inaccuracies: (1) clients don't search the internet for servers: the host is configured with servers (or picks them from a registry or allowlist), then calls server/discover and the list methods; (2) the standard transports are stdio and Streamable HTTP; WebSocket or message queues are custom or sit behind a server; (3) since 2026-07-28 there is no initialize handshake or session: every request carries its protocol version and client capabilities in _meta.

Types of MCP clients

Assistants that let users connect tools and data, with consent prompts per action.
