5 · Building agent systems

Harness, loop & graph engineering

Three ways to build agent systems: a harness to empower one agent, a loop to refine output, a graph to handle complex work. Most production systems nest them, for example a graph whose nodes are harnessed agents with internal loops.

Loop simulator

An evaluator–optimizer loop: draft, score, refine. Set the quality bar and the iteration budget. A good stop condition is the difference between self-correction and an infinite loop.

Which pattern fits?

Harness engineering: from powerful models to reliable results

A harness is the control system around a model: guides that raise the odds of a good first attempt, sensors that let the agent see and correct what it did, and state that lets work survive the end of a context window. The same model can produce broken or working software depending on what surrounds it.

Three agents around one prompt

Asked to grade their own work, agents confidently praise it, even when the quality is obviously mediocre. Anthropic's Labs team fixed this by separating the jobs: a planner writes the spec, a generator builds it a piece at a time, and an evaluator uses the running app like a user would and fails anything below the bar. Walk the loop.

Agent

Planner

Expands a 1–4 sentence prompt into a product spec: features, user stories, design. It stays at product level and leaves implementation to the generator. In the game run, one sentence became 16 features across ten sprints.

File

Sprint contract

Before any code is written, the generator and the evaluator agree what "done" means for the next piece of work and how it will be tested. The spec stays high level; the contract makes it testable.

Agent

Generator

Builds one feature at a time against the contract, commits with git, checks its own work, then hands off to QA. It never signs off on its own work.

Agent

Evaluator

Clicks through the running app with Playwright (through an MCP server), testing the UI, the API and the database. It files every bug against the contract. One sprint alone had 27 criteria.

Rule

Hard thresholds

Each sprint is graded on product depth, functionality, visual design and code quality. A score below the bar on any one fails the sprint, and detailed feedback goes back to the generator.

Lesson

Simplify as models improve

Every part of a harness encodes an assumption about what the model can't do alone. With a stronger model, the team dropped sprints entirely and the generator built for over two hours in one go. Re-test each part when the model changes.

A prompt that sets up the same loop in a coding agent such as Claude Code. Fill in the three braces; the rest runs as written.

THREE-AGENT HARNESS
{APP IN 1-4 SENTENCES} · {STACK} · {QUALITY BAR}

01 PLANNER
Expand {APP} into a product spec: features, user stories, design.
Stay at product level, no implementation details. Split into sprints.
02 CONTRACT
Before each sprint, write contract.md: what gets built, how it is tested.
The evaluator reviews it. Iterate until both agree on "done".
03 GENERATOR
Build one feature per sprint against the contract. Commit with git.
Self-check, then hand off to QA. Never sign off on your own work.
04 EVALUATOR
Click through the running app with Playwright, like a user would.
Test the UI, the API and the database. File every bug with file:line.
05 THRESHOLDS
Grade product depth, functionality, visual design, code quality.
Any score under {QUALITY BAR} fails the sprint. Feedback goes back.
06 LOOP
Fail, fix, retest. Update progress.md after every sprint.
Stop when every feature in the spec passes. Report cost and time.
Build the loop first, the evaluator second, orchestration last. Keep state outside the model, keep the action space small, and remove harness components as models improve. Related: harness vs loop vs graph, Claude Code dev kit.
