Vector search internals & long context vs RAG

Exact nearest-neighbor search compares the query with every vector, which is too slow at millions of chunks. Approximate nearest neighbor (ANN) indexes trade a sliver of recall for orders-of-magnitude speed. Step through an HNSW search, then decide when a long context window can replace retrieval.

Knobs that matter

HNSW: M & ef

M is links per node (more = better recall, more memory). ef_search is the candidate list size at query time: raise it for recall, lower it for latency.

IVF: nlist & nprobe

More cells (nlist) make each search smaller; probing more cells (nprobe) recovers recall.

Filters

Metadata filters (tenant, date, permission) can wreck ANN recall if applied after search. Prefer engines with filtered or pre-filtered HNSW.

Measure recall@k

Compare ANN results with exact search on a sample of queries. Tune until recall@10 meets your bar before tuning anything else.

Dimensions & quantization

Matryoshka embeddings let you truncate 3072 → 512 dims; int8 or binary quantization cuts memory further. Re-score the top results with full vectors.

Hybrid by default

Pair ANN with BM25 keyword search and fuse ranks. See RAG architectures.

Long context vs RAG

Million-token windows make it tempting to paste everything in. Sometimes that's right; often it's slow, expensive and less accurate. Use the calculator in Key formulas below to compare cost.
