Enterprise integration patterns

An agent is only as useful as the systems it can reach. Most enterprise work happens in CRM, ITSM, ERP and HR systems; reaching them safely means picking the right pattern, and making sure the agent acts as the user, with that user's permissions, rather than as an all-powerful service account.

Pick the pattern

PatternHow it worksUse whenWatch out for
Tool over APIThe agent calls a typed tool, often exposed through an MCP server, that wraps the system's REST or GraphQL API.The system has a documented API. The default choice.Rate limits, pagination, and tools that are too broad
Event-drivenThe system emits webhooks or events (case created, order shipped); the agent reacts or updates the conversation.Proactive notifications, long-running processesOrdering, retries and duplicate events (make handlers idempotent)
iPaaS / integration hubThe agent calls one integration layer that already connects many systems.The customer already runs an integration platformAn extra hop in latency; who owns the flows
Data sync for retrievalContent is synced into a search index with permissions attached.Read-heavy questions over documents and recordsFreshness and permission drift between source and index
UI automation (RPA)A bot drives the system's screens.Legacy systems with no API, as a last resortBrittle when screens change; slow; hard to secure

Identity: act as the user

Do

  • Sign users in with the customer's identity provider (SSO with OIDC or SAML)
  • Call systems with a token for that user: OAuth on-behalf-of or token exchange (RFC 8693)
  • Scope each tool to the least privilege it needs
  • Log every call with the user, the agent and the tool

Avoid

  • One admin service account for all users: the agent can then read what the user can't
  • Long-lived API keys inside prompts or tool code
  • Letting the model choose which identity to use
  • Writes without a confirmation step for anything irreversible
