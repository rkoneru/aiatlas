Multi-agent systems: swarms & orchestrators

A swarm is many agents that share information, divide work and adapt together. Done well, it solves tasks too broad or parallel for one agent. Done badly, it multiplies cost, latency and failure points. Start with one agent and add more only where the work genuinely splits.

Topology explorer

How agents are connected decides how much they talk, how fast information spreads and what breaks if one fails.

Types of swarms

Homogeneous

Identical agents splitting a big job (search, data collection).

Heterogeneous

Specialists: researcher, analyst, writer, critic.

Hierarchical

Manager and workers; the most common in production.

Decentralized

Peers with no leader; resilient, harder to control.

Adaptive

Structure changes with the task, adding or retiring agents.

Memory in swarms

Shared memory

A common store (blackboard) every agent reads and writes.

Distributed memory

Knowledge spread across agents and synced on demand.

Local memory

Each agent's private working context, kept small.

Evolving knowledge

Lessons from finished tasks written back for next time.

When to use a swarm

Good fit

  • Broad research where sub-questions can run in parallel
  • Work that needs different expertise or tools
  • Large jobs that split into independent parts
  • Exploration where several approaches should be tried

Poor fit

  • Tightly coupled tasks where every step depends on the last (such as most coding edits)
  • Low-margin, high-volume work: many agents means many more tokens
  • Tasks one well-equipped agent already handles
  • Anything without a way to check the combined result

Measuring a swarm

Task success

Did the swarm achieve the goal?

Output quality

Accuracy, relevance, usefulness.

Efficiency

Tokens, time and money per task vs one agent.

Robustness

Does it degrade gracefully when an agent fails?

Scalability

Does quality hold as agents are added?

Orchestrators & specialized agents

As agents grow, one prompt with every tool stops working. The fix is context engineering: a router or orchestrator understands the request and sends each part to a specialized agent that sees only the context it needs. Specialists rewrite the query, pick data sources, retrieve, call tools and synthesize the answer, while memory keeps working context small and long-term knowledge searchable.

Design principles

Intelligent routing

Each request goes to the best tool or agent, with a fallback for "unknown".

Adaptive execution

Plans change on results and real-time feedback.

Secure by design

Each specialist gets least-privilege tools; isolation between agents.

Observability

A historical log of actions, tool calls and decisions for audit and evals.

Reliable outcomes

All paths merge into one answer that's checked before delivery.
