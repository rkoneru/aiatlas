LLM serving & hardware

Serving an LLM is a memory problem as much as a compute problem. Prefill (reading the prompt) is compute-bound; decode (generating tokens) is bound by memory bandwidth. Serving engines squeeze GPUs with continuous batching, paged KV caches, fused attention kernels and prompt caching. Walk a request through an engine.

The techniques

Prompt caching

Don't re-read the same prefix

When many requests share a long prefix (system prompt, tool definitions, a document), the engine stores its processed KV state and reuses it. Providers usually bill cache hits at a fraction of the normal input price and cut time to first token. Keep the stable part first and byte-identical; put anything that varies after it.

Continuous batching

Fill every GPU slot

Static batching waits for the slowest request in the batch. Continuous (in-flight) batching adds new requests and removes finished ones at every decode step, raising throughput several-fold with little latency cost. Standard in vLLM, TGI, TensorRT-LLM and SGLang.

FlashAttention

Attention without the memory traffic

Computes attention in tiles that stay in fast on-chip SRAM instead of writing the full n×n matrix to GPU memory. Same result, much faster and far less memory, which is what made long contexts practical.

PagedAttention

Virtual memory for the KV cache

Stores each sequence's KV cache in fixed-size blocks, like OS pages, instead of one contiguous reservation. Almost no wasted memory, more concurrent requests, and shared blocks for common prefixes.

Prefill/decode split

Different jobs, different hardware

Large deployments run prefill and decode on separate GPU pools (disaggregated serving) and use chunked prefill so long prompts don't stall everyone's token stream.

Speculative & quantized

Fewer bytes, more tokens

Quantized weights (8-bit, 4-bit) mean fewer bytes per token; speculative decoding produces several tokens per big-model pass. See LLM optimization.

Rule of thumb: model weights + KV cache must fit in accelerator memory, and decode speed is roughly memory bandwidth ÷ bytes read per token. Use the calculators below.

Edge & on-device AI

Why on-device

Privacy (data never leaves the device), offline use, no per-token cost, and instant response for small tasks.

How

Small models (1–8B parameters) quantized to 4 bits, run through runtimes such as llama.cpp, Core ML, ONNX Runtime or vendor NPU SDKs.

Hybrid pattern

Handle simple requests on the device and escalate hard ones to the cloud, with the user's consent and clear disclosure.
